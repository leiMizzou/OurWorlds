# VoxelCraft 联机化设计方案

日期：2026-06-03
状态：待评审（已根据可行性评审修订）

## 1. 目标与范围

把单机的 VoxelCraft 做成**线上多人**游戏：

- **浏览器里就能玩**（免下载）
- **账号登录**
- **云端自动存档**（关掉浏览器，建造不丢）
- **大家在同一个世界一起玩**，目标是**公开、可容纳较多人**

非目标（明确不在本方案近期范围）：手机原生 App、语音、超大规模 MMO 同屏千人、复杂反作弊体系（公开前再加基础版）。

## 2. 核心判断（一句话）

> **游戏服务器本身就是 Godot。** 用 Godot 自带的高层多人 API，把现在的工程导出一个 **headless（无头）服务器版**当"权威服务器"，客户端连上去；两边共用同一套 GDScript。**只有"账号 + 入场票 + 云存档 + 大厅"需要单独的后端服务（Nakama）。**

关键边界：

- **Godot 客户端只和 Godot 世界服务器跑游戏 RPC**。Godot MultiplayerAPI 是 Godot 内部协议，不让 Nakama 直接解释游戏状态包。
- **Nakama 不做体素仿真**，只做账号、会话、入场票、世界列表、存储和管理 API。
- **客户端不直接写世界存档**。世界增量由 Godot 权威服务器校验后写入 Nakama/数据库。

## 3. 总体架构

```
            浏览器里的玩家（Godot Web/WASM 客户端）
                 │  ①登录/大厅/入场票     │  ②游戏连接(wss, Godot RPC)
                 ▼                         ▼
        ┌──────────────┐          ┌──────────────────────┐
        │   Nakama     │          │  反向代理 Caddy(TLS)   │
        │账号/票据/存档/大厅│        │  把 wss 路由到世界服务器 │
        └──────┬───────┘          └───────────┬──────────┘
               │                              │
          ┌────▼────┐              ┌──────────▼───────────┐
          │ Postgres│◀──服务端写存档│ Godot 世界服务器(headless,│
          │  数据库  │              │ 权威，多开=多个世界/分片) │
          └─────────┘              └──────────────────────┘
```

数据流：
1. 客户端在浏览器加载 → 用 **Nakama 登录**（邮箱/第三方/游客）拿到会话。
2. 客户端向 Nakama **要一个世界/服务器**（大厅或匹配）→ 拿到某台 Godot 世界服务器地址 + 入场票。
3. 客户端用 **WebSocket(wss)** 连到那台 Godot 世界服务器。
4. 世界服务器校验入场票 → 生成该玩家的小人 → 下发世界 ID、种子、玩家出生点和必要区块的改动增量。
5. 游戏中：客户端发"输入/编辑请求"，**服务器权威**校验后应用并广播。
6. 世界服务器**定时把脏区块增量 + 玩家数据落库**（优先经 Nakama 服务端 API；早期也可先本地文件/内存验证）。

## 4. 关键技术决策与理由

| 决策 | 选什么 | 为什么 |
|---|---|---|
| 联机传输 | **WebSocket**（`WebSocketMultiplayerPeer`） | 浏览器不支持原始 UDP/ENet。建造类游戏不抢帧，TCP 足够。WebRTC 留作以后降延迟的优化 |
| 拓扑 | **客户端-服务器（权威服务器）**，非 P2P | 一个权威方才好做"共享持久世界"和云存档，也是防作弊基础 |
| 世界服务器 | **headless Godot**（同一工程） | 复用 GDScript 仿真逻辑；避免另写一套游戏后端 |
| 账号/存档/大厅 | **Nakama**（开源游戏后端） | 自带登录、云存储、匹配/列表、好友、有官方 Godot SDK；仿真仍留在 Godot |
| 客户端 | **Godot 导出 Web(WASM)** | 浏览器免下载即玩 |
| 数据库 | **Postgres**（Nakama 自带依赖） | Nakama 存储基于 Postgres；不要一开始自建复杂 SQL 表 |
| 部署 | VPS + Docker + **Caddy(自动 TLS)** | 网页必须 https/wss；Caddy 自动证书、配置简单 |

## 5. 必要架构调整：先拆数据、渲染、网络入口

联机不是只在 `set_block()` 外面套 RPC；需要先把当前单机 `World` 的职责拆开，否则服务端会带着不必要的 Mesh/碰撞/相机逻辑一起跑。

建议拆成三层：

- **WorldData**：纯数据层。负责 seed、区块生成、`get_block()`、`apply_block()`、坐标换算。服务端和客户端共用。
- **WorldDeltaStore**：增量层。负责记录玩家改动、脏区块、序号、序列化/反序列化、按区块查询。M1 就需要内存版；M4 换成 Nakama 存储版。
- **WorldView**：渲染层。负责区块 Mesh、碰撞体、后台造网格、加载半径、卸载。主要运行在客户端；服务端只在需要物理校验时生成很小范围碰撞，避免全量渲染成本。

当前代码里的切入点：

- `WorldGenerator` 已有 seed 参数，但 `World.setup()` 现在固定 `WorldGenerator.new()`，需要改成可注入 seed。
- `World.set_block()` 现在直接改区块和重建网格，后续应拆成：
  - `request_edit()`：玩家/网络入口。
  - `apply_edit_authoritative()`：服务端校验并写增量。
  - `apply_edit_local()`：本地应用并触发重建。
- `Player` 现在点击后直接 `world.set_block()`；联机后改为请求网络层，单机模式则走本地模拟权威。

## 6. 世界怎么同步（本方案的关键巧思）

地形是**靠种子(seed)确定性生成**的，所以：

- **服务器永远不传基础地形**。客户端拿到种子后，用同一个 `WorldGenerator` 本地生成出一模一样的基础地形。
- 服务器只存 & 只传 **"方块增量"**：玩家把某格从"生成值"改成了别的，才记一条 `(x,y,z) -> 方块ID`。
- 增量**按区块组织**：客户端加载某区块时，向服务器要这个区块的改动，应用上去即可。
- M1 起就要有**内存增量表**。即使还不做云存档，区块卸载后再加载也必须能恢复玩家修改。
- 如果玩家把方块改回"生成值"，可以从增量表移除，避免存档无限膨胀。
- 如果玩家把原本有方块的位置挖成空气，空气本身也是有效增量，不能简单当作"无记录"。

编辑流程：

1. 客户端计算准星命中的目标格和放置格。
2. 客户端 `request_edit.rpc_id(1, world_id, pos, block_id, client_seq)`。
3. 服务器根据玩家位置、距离、方块合法性、频率限制、世界边界做校验。
4. 服务器写入 `WorldDeltaStore`，标记区块 dirty，生成递增 revision。
5. 服务器 `apply_edit.rpc(pos, block_id, revision)` 广播给相关玩家。
6. 客户端本地 `apply_edit_local()`，更新区块数据并重建本区块和边界邻居。

玩家同步：每个连接 = 一个小人。位置以 10-20Hz 同步；M1 可以用 `MultiplayerSynchronizer` 快速打通，M5 前建议评估手动同步 + 插值 + 兴趣管理，避免人多时广播过量。

## 7. 存档 / 云存档设计

不要把整个世界塞进一个巨大 JSON。推荐按世界和区块拆对象：

- `world_meta:{world_id}`：`{ seed, created_at, updated_at, rules, spawn }`
- `chunk_delta:{world_id}:{cx}:{cz}`：`{ revision, edits: { "lx,y,lz": block_id } }`
- `player_state:{world_id}:{user_id}`：`{ position, rotation, hotbar, selected_block, last_seen }`

原则：

- **服务端写，客户端读/请求**。客户端可以请求加载区块，但不直接写世界 delta。
- **脏区块批量保存**：服务器每 N 秒保存 dirty chunks；玩家离开时保存玩家状态。
- **按区块 revision 同步**：客户端记录自己已有的区块 revision，只请求缺的或旧的。
- **定期快照/压缩**：长期运行后，对高频编辑区块做压缩；把改回生成值的记录清掉。
- M1/M2 可以先只做内存版；M3 可以落本地 JSON 文件辅助测试；M4 再接 Nakama Storage。

这同时解决"关游戏建造就没了"：世界由服务器持有并持久化，客户端只是渲染副本。

## 8. 风险与对策（重要）

1. ⚠️ **网页性能（头号风险）**：体素在浏览器 WASM 里比桌面慢。多线程造网格在网页需安全上下文和跨源隔离响应头(COOP/COEP)，否则可能只能退回单线程。
   - 对策：在正式联机前加 **M0.5 Web 单机烟测**；网页版默认视距 3-4、限制世界高度；必要时做 greedy meshing、减少碰撞体、调低水/透明块成本。
2. ⚠️ **联机是架构升级**：当前 `World` 同时管数据、渲染、流式和编辑，服务端不能直接照搬客户端式世界。
   - 对策：先做 `WorldData + WorldDeltaStore + WorldView` 拆分；单机版始终保留可跑。
3. ⚠️ **服务端性能**：headless Godot 复用逻辑很省开发量，但如果服务端也建大量 Mesh/碰撞，会浪费 CPU/内存。
   - 对策：服务端默认不建可见 Mesh；只维护数据和玩家状态。编辑校验先用距离/规则，后续需要时再做小范围物理校验。
4. ⚠️ **公开 = 运维与成本**：服务器 24h 常开、要扩容、要防捣乱、要花钱。
   - 对策：起步一台小 VPS、邀请制；公开前再补限流、举报、封禁、备份、监控和日志。
5. ⚠️ **安全**：wss 必须 TLS；入场票校验；服务器对一切输入做校验（不信客户端）。
   - 对策：入场票短有效期；连接后绑定 peer/user/world；编辑频率限制；移动速度上限；异常行为记录。

## 9. 里程碑路线图

| 里程碑 | 内容 | 验证 |
|---|---|---|
| **M0** | **联机前架构拆分**：拆 `WorldData / WorldDeltaStore / WorldView`；`set_block` 拆成本地应用和请求入口；seed 可配置；单机模式继续可玩 | 单机测试全过；挖/放、流式加载、区块卸载后重载仍保留本局增量 |
| **M0.5** | **网页单机烟测**：导出 Web，验证 Godot 4 Web、线程、COOP/COEP、视距和 FPS | 浏览器里单机可玩；确认最低视距、帧率和加载卡顿 |
| **M1** | **本地双人共享世界**：headless 服务器(WebSocket) + 2 客户端；小人互见、挖/放实时同步；内存增量不丢；无账号/网页/云存档 | 本地开 1 服 + 2 客，互相看得见、改得动；远离再回来改动仍在 |
| **M2** | **网页客户端联机**：Web/WASM 客户端连本地或局域网 Godot 服务器 | 浏览器里能稳定联机 |
| **M3** | **服务器上云**：headless 服务器放 VPS，Caddy 配 wss/TLS；可选本地文件存档 | 公网地址可连；重启服务后测试世界恢复 |
| **M4** | **账号 + 云存档(Nakama)**：登录、入场票、chunk delta & 玩家数据落库、自动保存、重连续上 | 换设备登录，进入同一世界，建造还在 |
| **M5** | **大厅/多世界 + 兴趣管理**：Nakama 世界列表/匹配、多个 Godot 世界进程、附近玩家/区块同步 | 多人从大厅进不同世界；8-16 人压测 |
| **M6** | **公开加固**：反作弊校验、限流、举报、封禁、备份、监控、成本控制 | 可邀请制公开，问题可追踪、可恢复 |

**原则**：每个里程碑都能独立跑、能验证；单机版功能始终保留。

## 10. M0 详细方案（先铺地基）

**范围**：不做网络，只把单机代码改成适合联机的形状。

要改/要加：

- 新增 `WorldData`：纯数据区块管理，支持 seed、生成区块、应用方块修改。
- 新增 `WorldDeltaStore`：内存保存区块增量、dirty 标记、revision、序列化接口。
- 调整 `World`：保留为渲染/流式外壳，内部调用 `WorldData`。
- 调整编辑入口：
  - `apply_edit_local(pos, block_id)`：只应用事实。
  - `request_edit(pos, block_id)`：单机模式下直接调用本地权威；联机模式下发 RPC。
- 调整区块卸载逻辑：卸载只释放渲染节点和临时区块数据，不能丢本局增量；重新生成区块时要先生成基础地形，再套 delta。
- `WorldGenerator` seed 从默认值改成外部传入，后续由服务器下发。

验证方式：

- 单元测试：改一个方块 -> 卸载该区块 -> 重新加载 -> 方块仍是修改后的值。
- 单元测试：改回生成值 -> delta 被移除。
- 单机测试：现有操作、HUD、流式加载不退化。

## 11. M1 详细方案（第一步联机）

**范围**：一个世界、≤4 人、本地、WebSocket、无账号无云存档。先把"权威世界 + 同步"这块最难的打通。

要改/要加：

- **启动角色拆分**：游戏支持两种模式
  - *服务器*（headless）：建权威 `WorldData + WorldDeltaStore`，`WebSocketMultiplayerPeer.create_server(端口)`。
  - *客户端*：连接界面（填地址）→ `create_client(url)` → 进游戏。
  - 调试期支持"我开服并同时游玩(Host)"，方便一台机两个窗口测。
- **新增 `NetworkManager`**：封装多人初始化、`peer_connected/disconnected` 信号、入场流程、RPC 通道。
- **World 分"权威/副本"两态**：
  - 服务器：持有 seed + delta store，是唯一真相。
  - 客户端：本地按 seed 生成地形做渲染，应用服务器下发的 delta。
  - 编辑走 RPC：客户端 `request_edit.rpc_id(1, ...)` → 服务器校验+改 delta+ `apply_edit.rpc(...)` 广播 → 各端本地应用。
- **玩家同步**：服务器为每个 peer 生成一个小人；M1 可先用 `MultiplayerSpawner + MultiplayerSynchronizer`，后续再优化为手动同步/兴趣管理。
- **种子下发**：服务器定世界种子，进场时发给客户端，保证两边 `WorldGenerator` 一致。
- **连接界面**：一个简单主菜单场景：「开服并游玩 / 加入(填地址)」。

验证方式：

- 纯逻辑单测：模拟 `request_edit -> 校验 -> 改 delta -> 广播` 这条链，断言增量表正确、非法编辑被拒。
- 联网行为：本地开 1 个服务器 + 2 个客户端窗口，人工确认"互相看得见走动、看得见对方挖/放"。
- 持续性行为：客户端 A 改方块，离开该区块再回来；客户端 B 后加入，也能看到已有改动。

M1 明确不做：账号、云存档、网页导出、大厅、完整反作弊、兴趣管理、多人优化。

## 12. 待定 / 以后再定

- 登录方式（邮箱 / 第三方 / 游客）—— M4 再定；开发期建议先游客/设备 ID。
- 单个世界目标人数（影响后期优化，暂设 8-16）—— M5 再定。
- 云主机厂商 / 预算 / 域名 —— M3 再定。
- WebRTC 降延迟、greedy meshing、兴趣管理 —— 视 M0.5/M2 实测决定。
- 是否让服务端使用 Nakama Runtime RPC 写存档，还是 Godot 世界服直接调用 Nakama API —— M4 前做小实验。
